# Experiment structure

Each experiment folder contains:
- `index.html` - entry point (byte-identical across experiments; generated by `experiments/build/sync_entry_files.py`)
- `experiment.js` - thin call to `runExperiment()` from `_lib/bootstrap.js` (also generated by `build/sync_entry_files.py`)
- `trials.js` - only the study-specific `makeStimulusTrials`; exports `CONFIG` (via `makeConfig("<slug>")`), `INSTRUCTIONS_PAGES` (via `STUDY_INSTRUCTIONS["<slug>"]`), `COMPREHENSION_QUESTIONS` (via `STUDY_COMPREHENSION_CHECKS["<slug>"]`), and `makeStimulusTrials`

Most of each experiment is shared `_lib/` modules; `trials.js` just composes them:
- `bootstrap.js` — `runExperiment({ config, makeStimulusTrials, instructionsPages, comprehensionQuestions, consentTemplate })` assembles the whole timeline (consent → instructions + comprehension gate → stimulus trials → exit survey → save → thank-you). Timeline-wide changes go here, not in `trials.js`.
- `config.js` — `DATAPIPE_IDS` + shared `SHARED_CONFIG`; `makeConfig("<slug>")` merges them.
- `instructions.js` — `STUDY_INSTRUCTIONS` (all four studies' instruction pages in one place).
- `comprehension-check.js` — `STUDY_COMPREHENSION_CHECKS` (per-study quiz questions) + `makeComprehensionGate(jsPsych, {...})`. The gate replaces the standalone instructions screen: it shows the instructions then a `survey-multi-choice` check, gives the participant 3 attempts (re-showing the instructions on each miss), and ends the experiment with `jsPsych.abortExperiment` on a return-the-study message if they never pass — so failed participants save no data.
- `scenario.js` — per-trial building blocks (`getDesireText`/`getEffortText`, `intimacyDescriptor`, slider labels, `pressAnyKeyPage`, `blankPause`, `scenarioStimulus`).
- `two-slider.js` — `makeTwoSliderForm(...)` (two sliders on one page, Studies 1b/2b).
- `timeline.js`, `attention-check.js`, `memory-checks.js`, `style.css`, `consent/` — remaining boilerplate.

Each experiment references `_lib/` via `../_lib/`, so the active experiments are not standalone folders — `_lib/` must be deployed alongside them.

Experiments collect data via jsPsych-contrib/pipe plugin to `data/<experiment_name>/raw_data/`.

Config repeated across experiments is collected in [`experiments/_lib/config.js`](../../experiments/_lib/config.js): the `DATAPIPE_IDS` map (each experiment needs its own DataPipe ID — keyed by slug), the shared Prolific completion link, and the attention-check index/tolerance and inter-trial durations. Each `trials.js` calls `makeConfig("<slug>")` to merge the shared defaults with that experiment's DataPipe ID, passing overrides as a second argument when it needs to depart from a default.

## Deploy

Deploys go through [`bin/deploy-experiment`](../../bin/deploy-experiment), which rsyncs an experiment + `_lib/` to athena (`~/www/sip/experiments/`). Usage: `bin/deploy-experiment <slug>`. The script only accepts the four active slugs (Makefile's `EXPERIMENTS_INVERSE`): `food_inv_desire`, `food_inv_joint_de`, `food_inv_intimacy`, `food_inv_joint_ie`. See [experiments/README.md](../../experiments/README.md#deploying-experiments) for the full reference.

**Anti-drift guard.** A deploy only rsyncs what is on disk, so a forgotten regeneration would ship stale stimuli to participants. Before any push, `bin/deploy-experiment` regenerates all generated assets from source (`make experiments`: `scenarios.csv`, each `json/stimuli.json` + `json/full_counterbalancing.json`, and the entry files) and aborts if that changed anything — i.e. an asset was out of sync with its source of truth (`scenarios.py` / the `build/` generators). Run the check on its own with `make check-experiments` (or `bin/deploy-experiment --check-artifacts`) before committing experiment changes. It compares content before vs. after regenerating, so merely-uncommitted-but-current assets don't trip it; only genuine drift does. The SI scenario `.tex` tables are not part of this guard (they're not deployed and live in the gitignored `SIP_journal/` repo) — regenerate those separately with `experiments/export_scenarios_latex.py`.

## Scenario CSVs are generated from Python

The scenario CSVs are generated artifacts. Their source of truth is the corresponding `.py` file, which holds the scenario data as Python dicts and writes the CSV when run. Edit the `.py` file and regenerate with `uv run python experiments/<file>.py` — never edit the CSVs directly, since the next regeneration will overwrite the edits. The active set is `experiments/scenarios.py` → `scenarios.csv` (3-action); the non-food set is `experiments/scenarios_nonfood.py` → `scenarios_nonfood.csv`.

The paper's SI scenario tables are a further generated artifact downstream of the CSVs: `experiments/export_scenarios_latex.py` renders `scenarios.csv` / `scenarios_nonfood.csv` into `SIP_journal/si_scenarios_food.tex` / `si_scenarios_nonfood.tex` (each with an "AUTO-GENERATED — do not edit by hand" header). Don't read or edit those `.tex` files to inspect or change scenarios — go to the `.py` source, regenerate the CSV, then re-run the table export.

`scenarios.csv` is the 3-action canonical set for the inverse-planning experiments (Studies 1a, 1b, 2a, 2b). It carries the low_risk_share_effort_low/low_risk_share_effort_high paragraphs alongside the desire and intimacy framing so all three latent variables — desire, effort, intimacy — can be manipulated alongside the observed action. The three action columns are `no_share` / `low_risk_share` / `high_risk_share`.

Each experiment directory also has a per-experiment `json/stimuli.json` that is generated from one of the scenario CSVs. The routing from CSV to experiment dirs is in `experiments/build/csv_to_json.py` — run that after editing any scenario `.py` file to propagate changes into the experiments that consume it. (The build-time generators — `csv_to_json.py`, `counterbalancing.py`, `sync_entry_files.py`, plus the shared `_scenario_io.py` writer — all live in `experiments/build/`; the authored scenario data stays at `experiments/scenarios.py`.)
